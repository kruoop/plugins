# 🍀 ติดตั้งและตรวจงานด้วย Ponytail
## ทำไมต้องทำแบบนี้
AI เขียนโค้ดได้เร็ว แต่บางครั้งสร้างไฟล์ ระบบตั้งค่า หรือ dependency มากกว่างานที่ต้องใช้ Ponytail เป็นกติกาให้หยุดคิดก่อนสร้างของใหม่ ไม่ใช่โมเดล AI ตัวใหม่ค่ะ

เปรียบเหมือนช่างที่ตรวจว่ามีอะไหล่มาตรฐานอยู่แล้วไหมก่อนสั่งทำชิ้นใหม่ ส่วน Claude Code เป็นคนลงมืออ่าน แก้ไฟล์ และรันทดสอบ ข้อเสียคือโค้ดสั้นไม่ได้แปลว่าถูกเสมอ ยังต้องตรวจพฤติกรรมจริงและอ่าน diff

## Workflow
1. เลือกโฟลเดอร์งานที่ถูกต้อง
2. ↓ อ่านไฟล์เดิมและกำหนดผลลัพธ์ที่ต้องการ
3. ↓ เพิ่ม Marketplace แล้วติดตั้ง Ponytail
4. ↓ ตรวจสถานะ Plugin และ Hook
5. ↓ สั่งงานเล็กที่วัดผลได้
6. ↓ เปิดผลลัพธ์จริงและรันทดสอบ
7. ↓ รีวิว diff ก่อนยอมรับงาน

## เครื่องมือ
- **Claude Code ใน Desktop** — อ่านและแก้โปรเจกต์ local
- **Ponytail** — กติกาเลือกใช้ของเดิมและเขียนเท่าที่จำเป็น
- **Node.js** — runtime สำหรับ lifecycle hooks ตามข้อกำหนด repository ต้องเข้าถึงได้ใน PATH ของแอป
- **Matt Pocock Skills** — ชุดเสริมที่คลิปทดลองเพิ่ม ไม่จำเป็นสำหรับการเริ่ม Ponytail ขั้นพื้นฐาน
- **Browser/Preview** — เปิดตรวจเว็บที่สร้างจริง

ลิงก์และคำสั่งอยู่ในแท็บ 💎 ค่ะ

## เปิดโปรเจกต์
เปิด Claude Desktop แล้วเลือก Code ใช้ Open folder เลือกโฟลเดอร์ทดสอบของคุณ ตรวจว่า project ชี้ไปที่โฟลเดอร์นี้ก่อนส่งคำสั่ง หากมี Trust this workspace ให้อนุญาตเฉพาะงานที่เชื่อถือได้ ไม่กดยืนยันทุกโฟลเดอร์ที่ดาวน์โหลดมา

## ติดตั้งตามลำดับ
1. เปิด repository Ponytail และตรวจชื่อเจ้าของ DietrichGebert ให้ตรง
2. ส่งคำสั่งเพิ่ม marketplace จากแท็บ 💎 ก่อน
3. อ่านผลตอบกลับว่าสำเร็จ ไม่ใช่ยัง queued/running
4. ส่งคำสั่ง install แยกเป็นอีกข้อความ
5. ตรวจรายการ Plugin ว่าติดตั้งแล้ว และอ่านสิทธิ์ก่อนอนุญาต

ในตัวอย่าง Desktop ผู้บรรยายตัด slash หน้า command เพื่อส่งเป็นข้อความให้ Claude ช่วยติดตั้ง หากแอปของคุณไม่รับ slash command ให้ใช้เมนู Plugin/Install ที่แสดงจริง ไม่ถือว่า Desktop ทุกเวอร์ชันทำงานเหมือนกัน

## ตรวจ Hook ก่อนเชื่อว่าอัตโนมัติ
การสั่งให้ใช้ Plugin ทุก session ไม่ใช่หลักฐานว่า Hook ทำงานทุก session ค่ะ เริ่มแชตใหม่ในโฟลเดอร์ทดสอบ ตรวจ log หรือสถานะการเรียกใช้ แล้วลองงานเล็กที่มีของเดิมให้ reuse

หากไม่ทำงาน ให้ตรวจ Node/PATH และขอบเขต project/global ก่อนแก้ config ไม่เขียนทับ settings.json ทั้งก้อน และไม่ติดตั้งซ้ำเพื่อกลบอาการ ข้อความ Running tools หรือ message queued บอกแค่ว่ากำลังทำหรือรอคิว

## ทดลองสร้างเว็บ 3D
ใช้ Prompt ทดลองในแท็บ 💎 เพื่อสร้างหน้า HTML ที่มีโมเดลม้า 3D เริ่มจากของเดิมและ dependency ที่มีอยู่ก่อนเพิ่มของใหม่ ให้ AI เปิดผลลัพธ์และลองตัวควบคุมที่หน้าเว็บมีจริง

ตรวจให้ครบว่าไฟล์เกิดในโฟลเดอร์ที่เลือก หน้าเว็บเปิดได้ หมุน/ซูมได้ตาม requirement และไม่มี error ที่ทำให้ใช้งานไม่ได้ ถ้ายังไม่ได้รัน อย่าเรียกงานว่าเสร็จ

## อ่านค่าประมาณให้ถูก
ตารางในตัวอย่างมีช่องป้อนจำนวนบรรทัด จำนวนไฟล์ token ต่อบรรทัด ราคา เวลา และบั๊กต่อจำนวนบรรทัด ค่าที่ใส่ในตารางไม่เท่ากับค่า usage หรือผลทดสอบจริงของสองรอบที่ควบคุมเงื่อนไขเหมือนกัน

อย่าใช้จำนวนบรรทัดแทนความแม่นยำ และอย่าใช้ตัวคูณต้นทุนต่อบรรทัดแทนใบเสร็จค่าบริการ หากไม่มี baseline ให้รายงานเฉพาะรอบที่ทำจริง ไม่สร้างตัวเลขอีกฝั่งให้ตารางดูครบ

## ข้อควรระวัง
- ความสั้นไม่อนุญาตให้ตัด validation, error handling, security หรือ accessibility
- อ่านโค้ดและสิทธิ์ของ Plugin/Hook ก่อนใช้กับข้อมูลจริง
- ไม่ส่ง API key, password, OTP หรือข้อมูลบัตรเข้า prompt ให้เจ้าของบัญชีกรอกข้อมูลลับเอง
- ปิดชื่อโปรเจกต์ local path และข้อมูลลูกค้าก่อนอัดหน้าจอ
- เลือก skills ที่ใช้จริงและหลีกเลี่ยงติดตั้งชุดเดียวกันซ้ำหลายช่องทาง
- ผล benchmark ของผู้พัฒนาไม่ใช่คำรับประกันว่าทุกงานจะประหยัดเท่ากันหรือปลอดภัยทั้งหมด

# 🔥 ต่อยอด Exclusive
## 🧪 สองรอบที่เทียบกันได้ ดีกว่าตารางที่เดาตัวเลข
ใช้สำเนาโปรเจกต์เดียวกันสองชุด กำหนด requirement และโมเดล/setting เดียวกัน แล้วทดลองแบบใช้กับไม่ใช้ Ponytail โดยเก็บหลักฐานจริง ไม่ใช้จำนวนบรรทัดที่ AI คาดเดาเป็น baseline ค่ะ

## เก็บสถานะให้ตัดสินใจได้
- **ยังไม่รัน** — มีไฟล์หรือคำตอบแล้ว แต่ยังไม่มีหลักฐานการใช้งาน
- **รันแล้ว** — เปิดงานหรือทดสอบได้จริง บันทึกผลและ error
- **ผ่าน requirement** — ผลทดสอบครบพฤติกรรมที่ตกลงไว้
- **พร้อมส่ง** — รีวิว diff ข้อมูลส่วนตัวและข้อจำกัดแล้ว

อย่าข้ามจาก “สร้างไฟล์แล้ว” ไป “พร้อมส่ง” เพราะโค้ดสั้นลง เก็บ elapsed time และ usage ที่เครื่องมือรายงานแยกจากค่าประมาณเสมอ

## ลดความเสี่ยงของการวัด
ใช้ requirement ที่เช็กได้ เช่น เปิดหน้าได้ หมุนโมเดลได้ และไม่มี runtime error รันแต่ละแบบมากกว่าหนึ่งครั้งหากจะสรุปแนวโน้ม พร้อมเก็บความต่างระหว่างรอบ ไม่อ้างผลจากตัวอย่างเดียวเป็นกฎสากล

## 💼 เปลี่ยนเป็นงานบริการที่ส่งมอบชัด
เสนอแพ็กเกจปรับงานเล็กที่มีเกณฑ์รับ เช่น ลดโค้ดซ้ำโดยยังผ่านการทดสอบเดิม ส่ง diff, ผลรัน และวิธีย้อนกลับ แทนการขายคำสัญญาว่าประหยัด token เป็นเปอร์เซ็นต์ตายตัว

แยกเวลาทำงาน ค่าบริการ AI และงานนอกขอบเขตในข้อตกลง ไม่คำนวณกำไรจากค่าประมาณที่ไม่มีใบใช้งานจริงรองรับ

❓ ติดปัญหาตรงไหน โพสต์ถามได้เลยที่แท็บ Community พร้อมแนบข้อความ error ที่เจอ ผมและเพื่อนสมาชิกจะช่วยกันดูให้ครับ
